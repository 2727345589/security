# RB-003 数据泄露 / 数据外泄

| 项 | 内容 |
|---|---|
| Runbook ID | RB-003 |
| 版本 | v1.0 |
| 负责人 | DPO / 数据安全负责人 |
| 最后演练 | 待定（建议每年） |
| 默认级别 | **P1 紧急** |
| 关联 | `../30-sensitive-data-exposure/`、`../51-insider-threat/`、`../40-logging-monitoring/` |

## 1. 触发条件

- DLP 告警：批量导出、外发敏感数据
- 公开存储桶 / 公开数据库 / 公开 API 被发现
- 外部研究者、客户、媒体告知数据可被访问
- 暗网/论坛出现组织数据样本
- 异常外联（大流量上传到陌生地址、DNS 隧道）
- 内部人员举报或离职审计发现异常下载
- 供应商通知其系统被入侵且涉及我方数据

## 2. 分级与响应时限

| 情形 | 级别 | 首次响应 |
|---|---|---|
| 正在外泄 / 大规模个人信息 / 敏感数据 | P1 | 15 分钟 |
| 已停止外泄但范围不明 | P1 | 30 分钟 |
| 小范围、可快速控制 | P2 | 1 小时 |
| 仅疑似（如公开链接但无访问记录） | P3 | 4 小时 |

## 3. 角色与职责

| 角色 | 职责 |
|---|---|
| Incident Commander | 统一指挥、决策 |
| 数据安全/DPO | 定级、合规判断、上报 |
| 法务 | 法律责任、监管沟通、证据要求 |
| 系统/运维 | 关闭暴露面、取证 |
| 业务负责人 | 评估业务影响、通知客户 |
| PR | 对外口径 |
| 客服 | 用户咨询应答 |

> **注意**：数据泄露的「是否上报」由法务/DPO 判断，技术人员不要自行决定或对外承诺。

## 4. 前置准备

- [ ] 数据分类分级清单（哪些是个人信息/敏感个人信息/商业秘密）
- [ ] 数据地图（存在哪、谁能访问、保留多久）
- [ ] 各法域上报时限表（如 GDPR 72 小时）
- [ ] 对外通知模板（监管版 / 用户版 / 媒体版）
- [ ] 取证工具与只读存储
- [ ] 保险与外部律师联系方式

## 5. 处置步骤

### Step 1 止血（0–30 分钟）

```text
1. 关闭公开访问：存储桶策略、共享链接、API 权限、数据库白名单
2. 撤销泄露的凭据/Token（见 RB-007）
3. 若为内部人员：暂停账号、回收权限（先保全证据再禁用）
4. 若为外泄流量：封禁目标地址、限制出网
5. ⚠️ 不要删除数据、不要重置环境——会破坏证据
```

```bash
# 只读：确认暴露面（示例）
curl -sI https://api.example.com/export | head -20
aws s3api get-bucket-acl --bucket company-data
aws s3api get-bucket-policy --bucket company-data
```

```bash
# ⚠️ 双人确认：关闭公开访问
aws s3api put-public-access-block --bucket company-data \
  --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
```

### Step 2 保全证据（30–90 分钟）

```text
1. 记录发现时间、发现人、发现方式
2. 保存访问日志（谁在何时访问了什么）
3. 保存公开页面快照（截图 + 原始 HTML + 哈希）
4. 保存外联 PCAP / 代理日志
5. 保存内部人员操作审计
6. 所有证据计算 sha256，存只读介质，登记证据链
```

```bash
mkdir -p /cases/RB-003-$(date +%Y%m%d) && cd $_
# 快照与哈希
curl -s https://leaked.example.com > snapshot.html
shasum -a 256 snapshot.html > snapshot.sha256
# 导出访问日志（示例）
aws s3api get-bucket-logging --bucket company-data
```

### Step 3 界定范围（关键，1–24 小时）

填写范围工作表：

| 问题 | 答案 |
|---|---|
| 泄露了哪些数据类别？ | 姓名/手机/身份证/银行卡/健康/位置/账号密码/源代码… |
| 涉及多少人？ | 精确或估算，说明方法 |
| 是否可直接识别个人？ | 是 / 否（可结合其他数据识别） |
| 数据是否加密？密钥是否也泄露？ | |
| 泄露持续时间？ | 首次暴露 → 关闭时间 |
| 谁访问过？ | 日志中的 IP/账号，是否有下载 |
| 是否已被公开传播？ | 暗网/论坛/搜索引擎缓存 |
| 是否涉及跨境？ | 影响适用法域 |

> 不确定时按「已泄露」处理，宁可高估。

### Step 4 合规判断（与法务/DPO 同步）

```text
1. 是否属于「个人信息泄露」？是否属于「敏感个人信息」？
2. 适用哪些法域？上报时限？
   - 中国：《个人信息保护法》《网络数据安全管理条例》——立即采取补救，通知履职部门和个人
   - 欧盟 GDPR：知悉后 72 小时内通知监管
   - 美国：州法各异（如加州 CCPA），注意各州时限
3. 是否需通知个人？通知内容、方式、时限
4. 是否需通知监管、公安、行业主管？
5. 是否触发合同中的通知义务（客户/供应商）？
```

### Step 5 清除与修复

```text
1. 修复根因：权限、配置、漏洞、内部流程
2. 清理公开副本：搜索引擎缓存、代码仓库、公开链接
3. 强制相关账号改密、轮换密钥
4. 加强监控：该数据集访问告警、暗网监控
5. 若为供应商导致：启动供应商联合处置
```

### Step 6 通知

| 对象 | 负责 | 要点 |
|---|---|---|
| 监管 | 法务/DPO | 按法域时限，事实清楚，不推测 |
| 受影响个人 | 业务/客服 | 发生了什么、可能影响、应采取的措施、联系方式 |
| 客户/合作方 | 业务 | 合同义务，统一口径 |
| 公众/媒体 | PR | 由 IC 批准，避免二次伤害 |
| 执法 | 法务 | 报案回执 |
| 保险 | 风控 | 时限与材料要求 |

### Step 7 复盘（5–10 个工作日）

```text
1. 根因：技术漏洞 / 配置错误 / 内部人员 / 供应商
2. 检测时延：从暴露到发现多久？为何？
3. 响应时延：从发现到止血多久？
4. 改进项：权限、DLP、监控、流程、培训
5. 更新数据地图与分类分级
```

## 6. 验证标准

- [ ] 暴露面已关闭，外部无法再访问
- [ ] 泄露凭据已全部失效
- [ ] 访问日志已保全，范围已界定
- [ ] 合规通知已按法域完成（或已记录不通知的理由）
- [ ] 受影响用户已通知（如需）
- [ ] 根因已修复，监控规则已上线
- [ ] 证据链完整、可审计

## 7. 升级与通知

- 涉及敏感个人信息 / 大规模 → 立即升级 P1，1 小时内召集 IC + 法务 + DPO
- 涉及正在外泄 → 先断外联，再评估
- 涉及执法调查 → 所有操作经法务确认
- 媒体已报道 → 启动 PR 危机流程

## 8. 沟通模板

```text
【用户通知 · 数据安全事件】
尊敬的用户：
我们于 ____ 发现一起数据安全事件，可能涉及您的以下信息：____。
我们已采取的措施：____。
建议您：1) 留意异常来电/短信；2) 如涉及密码，请立即修改并启用 MFA；3) 警惕以本事件为由的二次诈骗。
如需帮助请联系：____。
我们对由此带来的不便深表歉意。
```

> 禁止：隐瞒、淡化、承诺「绝对安全」、未经法务确认披露细节。

## 9. 取证与保全

| 证据 | 说明 |
|---|---|
| 暴露快照 | 页面 HTML、截图、时间戳、哈希 |
| 访问日志 | 存储/应用/WAF/代理日志 |
| 账号操作 | 导出、下载、共享、权限变更 |
| 外联流量 | PCAP、NetFlow、DNS 查询 |
| 内部人员 | 终端操作、打印、USB、邮件 |
| 沟通记录 | 发现人陈述、供应商通知 |

## 10. 恢复与复盘

- 恢复前确认根因已修复，避免二次泄露
- 对受影响数据集加密/脱敏/最小化
- 建立「数据访问异常」长期监控
- 复盘报告归档，满足合规审计要求
